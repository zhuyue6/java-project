## 讲解

四个模块用同一套分层。这节不再介绍注解，只回答「这条业务在哪决定」。

### 1. 用户：分层最完整的样板

入口 `UserController`，前缀 `/users`。

| 接口 | 行为 |
| --- | --- |
| `GET /users/{id}` | `requireUser`，没有则 11001。返回 `UserResponse` |
| `GET /users` | query 绑定 `UserListRequest`，Service 算 offset，返回 `PageResponse` |
| `POST /users/{id}/avatar` | 文件进 `StoreageService`，URL 写回 `user.avatar_url`。写入对象是 token 里的用户 |

列表的 keyword、status、分页 SQL 在第 5 课已经对过。后面改目标列表时，照着 `UserWhere` 的 `<if>` 写。

### 2. 目标：登录用户贯穿每一次调用

入口 `GoalController`，前缀 `/goals`。每个方法都取 `LoginUser`，把 `userId` 传进 Service。

| 接口 | Service 在做的事 |
| --- | --- |
| `POST /goals` | 用到期时间和周期算出应打卡次数，插入 `goal`，返回新 id |
| `GET /goals` | 查该用户全部目标，配上标签名称，逐条转换成 `GoalResponse` |
| `GET /goals/{id}` | 按 userId + id 查。XML 查不到则返回 null |
| `PATCH /goals/{id}` | `requireGoal`，没有则 14001；按创建时间重算应打卡次数 |
| `DELETE /goals/{id}` | 同样 `requireGoal`，再按 userId + id 删除 |
| `POST /goals/{id}/clockIn` | 打卡次数加 1 后更新。新接口路径按 `POST /goals/{id}/clock-ins` 命名 |

创建时的次数计算在 `TimeService.getTimeDifference`：

| `clockInCycle` | 单位 |
| --- | --- |
| 1 | 从当前时间到到期时间的天数 |
| 2 | 周数 |
| 3 | 月数 |

`CreateGoalRequest` 把周期限制在 1 到 3。请求里的 `expirationTime` 是字符串 `yyyy-MM-dd HH:mm:ss`，进 Service 后已是 `LocalDateTime`。

响应里的状态是算出来的，方法是 `getGoalStatus`：

| 返回值 | 条件 |
| --- | --- |
| 2 | 已打卡次数达到目标次数 |
| 3 | 当前时间晚于到期时间 |
| 1 | 其余情况，进行中 |

完成优先于过期：次数已经达标时返回 2，即便日期已过。`calculateCompletionRate` 用次数相除，保留两位小数。

列表接口把该用户的标签一次查出，再按 `labelId` 填到每条目标上。标签服务因此被 `GoalServiceImpl` 注入。这是模块之间通过 Service 协作，目标模块不直接调用 `LabelMapper`。

`GET /goals/{id}` 在目标不存在时返回 null，成功响应的 `data` 为 null。`PATCH` 和 `DELETE` 走 `requireGoal`，不存在时是 14001。走读时把这两个差异指出来：同一次「找不到」，列表详情和修改删除的约定不相同。改接口时沿用修改那条，找不到就抛 `GoalNotFound`。

数据层已有 `user_id` 条件。练习里新增的 SQL 继续带上 `userId`。

### 3. 标签：一条规则产生 13001

入口 `LabelController`，前缀 `/labels`。

`createLabel` 的规则在 `LabelServiceImpl`：取出该用户全部标签，名称和类型都相同则抛 `LabelNameAlreadyExists`（13001），否则 `insertLabel`。比较发生在内存里的这一轮列表上，插入语句本身没有唯一索引判断。

`GET /labels` 只返回当前用户的标签。`GET /labels/{id}` 按主键查，方法参数里没有 `LoginUser`。走读时标出这个差别：列表和创建绑定了用户，按 id 查询当前没有按用户过滤。

删除 `DELETE /labels/{id}` 把 userId 和 id 一起交给 Mapper。

### 4. 管理端：另一个 accountType，复用用户服务

入口分两个 Controller：

- `AdminAuthController`，`/admin/auth`。登录标了 `@IgnoreJwt`，签发 `accountType=admin` 的 token。
- `AdminPlatformUserController`，`/admin/users`。列表、详情、改状态。这些方法没有 `@IgnoreJwt`，要带管理员 token。C 端 token 会被拦截器拒绝。

列表并不重写 SQL。`AdminPlatformUserServiceImpl.getUserList` 把管理端的查询对象抄成 `UserListRequest`，调用 `userService.getUserList`。分页和 keyword 行为与 `GET /users` 相同，差别在路径和 token 种类。

详情 `GET /admin/users/{id}` 会再查这个用户的目标和标签，汇总进行中、已完成、已过期的个数，并带上最近的目标。状态个数来自 `GoalResponse.status`，也就是上一节那个计算方法。

停用：

```http
POST /admin/users/{id}/status
Authorization: Bearer <admin token>

{ "status": 0 }
```

实现是 `userService.updateUserStatus`：更新 `user.status`，并刷新 Redis 键 `user:status:<id>`。该用户下一请求在 `GlobalAuthInterceptor` 得到 11004。这就是「管理端的一次写操作，立刻影响 C 端」的完整路径。

管理端登出标了 `@IgnoreJwt`，和 C 端登出不同。C 端登出先过拦截器。讲的时候把第 6 课的表再对一次即可。

### 5. 课堂要改的接口

在 `GET /goals` 上增加可选查询参数 `keyword`，按备注模糊筛选，并且只返回当前用户的目标。

行为：

- `GET /goals`：与现在相同，返回该用户全部目标。
- `GET /goals?keyword=跑步`：备注中包含「跑步」的目标。
- `keyword` 为空或没有该参数：不加 LIKE 条件。
- 仍然从 `LoginUser` 取 userId。请求里出现 `userId` 也不采用。
- 找到 0 条时 `code` 为 0，`data` 为 `[]`。

建议落点，对照用户列表：

1. 新增 `GoalListRequest`，放在 `modules/goal/dto/request/`。里面一个 `String keyword`。这是 GET query，Controller 用 `@ModelAttribute` 接收。若要校验字符集，注解和 `@Valid` 的写法照 `UserListRequest`。
2. `GoalController.getGoals` 增加这个参数，把 `keyword` 和 `userId` 传给 Service。
3. `GoalService.getGoals` 的签名加上 `keyword`，实现类传给 Mapper。标签匹配、`convertToGoalResponse` 保持原样，只是输入列表变短。
4. `GoalMapper` 增加带 `@Param("userId")`、`@Param("keyword")` 的查询方法；XML 用 `<if test="keyword != null and keyword != ''">` 拼接 `AND remark LIKE CONCAT('%', #{keyword}, '%')`，WHERE 里保留 `user_id = #{userId}`。

可以复用现有 `selectGoalByUserId` 并给它加参数，也可以新写一个 id。改现有方法时，把所有调用点一起改掉，避免接口和 XML 的参数对不上。

完成率、状态仍在 Service 里计算。这次练习不把 `status` 放进 SQL，避免和 `getGoalStatus` 的实时计算结果分成两套。

早期路径 `/clockIn` 这次不动。

## 课堂练习

1. 用 C 端 token 走一遍：创建标签 → 创建目标（带 `labelId`、到期时间、周期）→ `GET /goals` → `POST /goals/{id}/clockIn` → 再 `GET`，确认 `clockInCount` 增加，`completionRate` 变化。
2. 用同一 token 再创建一个同名同类型标签，确认 13001。
3. 完成上一节的 `keyword` 筛选，并用三组请求验证：不传 keyword、传能命中的备注、传命中不了的备注。再用另一个用户的 token 确认看不到第一个用户的目标。
4. 用管理员 token 打开 `GET /admin/users/{id}`，对照该用户的目标列表，看汇总里的进行中 / 已完成 / 已过期是否与 `getGoalStatus` 的规则一致。

## 下课前对一下

- 用户模块是分层样板；目标模块演示 token 里的 userId 如何进入每一条 SQL。
- 目标状态和完成率在 `GoalServiceImpl` 计算；标签重名在 `LabelServiceImpl` 抛 13001。
- 管理端列表复用 `UserService`，停用用户会写数据库和 Redis，C 端下一次请求得到 11004。
- 给列表加筛选时，新增或扩展 Request，Service 传参，XML 用 `<if>` 和 `#{keyword}`，条件里始终带当前用户 id。
