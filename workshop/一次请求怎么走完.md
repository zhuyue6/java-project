# 一次请求怎么走完：给前端的 Java 后端速览

面向刚开始写 Java 后端的前端。前半用「已登录用户创建一个目标」把整条链路讲完，后半补分页、目标状态、标签、管理端，并当场改一处查询。这里只列要点，展开时直接打开对应的类。

业务代码在 `clock-my-goal`。

## 整条链路

```text
浏览器  /api/...
  → Nginx 去掉 /api
  → 应用 :9090
  → GlobalAuthInterceptor.preHandle
  → GoalController.createGoal
  → GoalServiceImpl
  → GoalMapper.xml → MySQL goal 表
  → GlobalResponseHandler 包成 { code, message, data }
```

失败进 `GlobalExceptionHandler`，JSON 形状相同。

顺序：拦截器 `preHandle` → Controller →（异常则 Advice）→ 响应包装 → 拦截器 `postHandle`。

打开：`docker/nginx/nginx.conf`、`GoalController`、`GlobalAuthInterceptor`、`GlobalResponseHandler`。

## 工程与分层

根目录 `pom.xml` 是父工程，管 JDK 和依赖版本。可运行的是模块 `clock-my-goal`。进程从 `Application.java` 的 `@SpringBootApplication` 启动，扫描包 `com.zhuyue.clockMyGoal`。

一个业务模块里这几层：

| 层 | 作用 |
| --- | --- |
| `controller` | 接 HTTP |
| `service` / `service.impl` | 业务规则 |
| `mapper` + `resources/mapper/*.xml` | SQL |
| `entity` | 和表对应 |
| `dto.request` / `dto.response` | 入参 / 返回给前端 |

配置在 `application.yaml`。`${DB_URL}` 这类占位由环境变量填，容器里的值在 `docker-compose.yaml`。表在 `docker/mysql/init/init.sql`：`user`、`goal`、`goal_label`、`admin_user`。

## 请求怎么进到方法

`@RestController` 加上方法上的 `@GetMapping`、`@PostMapping` 等，就是路由。类上的路径和方法上的路径拼在一起。Controller 返回业务对象，外面再包一层统一 JSON。

现行路径看 `UserController`：

| 动作 | 方法 | 路径 | 参数位置 |
| --- | --- | --- | --- |
| 列表 | GET | `/users` | query，`pageNum`、`pageSize` |
| 详情 | GET | `/users/{id}` | 路径 |
| 创建 | POST | `/users` | JSON |
| 部分更新 | PATCH | `/users/{id}` | JSON |
| 删除 | DELETE | `/users/{id}` | 路径 |

登录、注册、登出走 `POST /auth/login`、`/auth/register`、`/auth/logout`。

入参注解：`@PathVariable` 路径，`@ModelAttribute` 查询串，`@RequestBody` JSON，`@RequestHeader` 请求头。

当前用户来自 `@RequestAttribute("userInfo") LoginUser`，里面是 `userId` 和 `userName`。`GoalController.createGoal` 的 body 是目标字段，用户 id 用 token 里的，不采用客户端另外传的 userId。

浏览器里的 `/api/goals`，到 Controller 时是 `/goals`。本机直连 `9090` 不加 `/api`。

## 入参、返回和错误码

三种对象分开：

- Request：客户端提交的字段，校验写在字段上。目标的到期时间格式是 `yyyy-MM-dd HH:mm:ss`。
- Entity：对齐数据库表，可以含密码。
- Response：给前端。用户响应里没有密码，时间是字符串。

校验在进方法前执行，条件是参数上有 `@Valid`。`POST /goals` 有。`POST /auth/login` 的 DTO 上有注解，参数上没有 `@Valid`，那些注解不会先跑。

成功由 `GlobalResponseHandler` 包成：

```json
{ "code": 0, "message": "操作成功", "data": ... }
```

`data` 就是 Controller 的返回值。`void` 时 `data` 为 `null`。分页列表在 `data.data`。

失败抛 `BusinessException`，由 `GlobalExceptionHandler` 收成同一形状。

| code | 含义 |
| --- | --- |
| 0 | 成功 |
| 10004 | 未登录 |
| 10005 | 登录过期或已登出 |
| 10006 | 参数错误，`message` 用字段上的文案 |
| 11004 | 账号已停用 |
| 13001 | 同一用户、同一类型下标签名已存在 |
| 14001 | 目标不存在 |
| 15002 | 管理员用户名或密码错误 |

前端按 `code` 分支。缺 token、JWT 过期、账号停用时 HTTP 状态会是 401。token 已进黑名单时，以 JSON 里的 10005 为准。

打开：`CreateGoalRequest`、`User`、`UserResponse`、`ApiResponse`、`ExceptionCodeEnum`。

可以当场对三次失败：`GET /users` 不带分页，看 10006 和「页码不能为空」；`POST /goals` 不带 `expirationTime`，看字段文案；`expirationTime` 写成 `2026/12/31`，进不了字段校验，仍是 10006，文案是「参数错误」。

## 规则和数据库

Controller 注入接口：`@Resource(name = "GoalService")`，实现类上是 `@Service("GoalService")`。

创建目标时 Service 做两件事：把请求抄进 `Goal`，算出应打卡次数；再调用 `goalMapper.insertGoal(userId, goal)`。用户 id 是单独参数，来自 token。

XML 对上两处：`namespace` 是 Mapper 接口全类名，标签 `id` 是方法名。`#{userId}` 对应 `@Param`，`#{goal.remark}` 是名为 `goal` 的对象上的属性。`useGeneratedKeys` 且 `keyProperty="goal.id"` 时，自增主键写回对象，再返回给前端。

列名下划线、字段驼峰，靠 `application.yaml` 里的 `map-underscore-to-camel-case`。

列表的可选条件在 XML 的 `<if>` 里，值为空就不拼进 SQL。参数用 `#{}`。

查不到业务数据时，在 Service 抛 `BusinessException`，例如 `GoalNotFound`。

本仓库登录用字符串和库里的密码直接比较，密码按原样入库。这是学习项目的写法，上线前要改成哈希。

打开：`GoalServiceImpl.createGoal`、`GoalMapper.xml` 的 `insertGoal`。用户列表的动态条件看 `UserMapper.xml`。

## 登录态

登录成功后 `JwtService.generateToken` 写入用户 id、用户名、`accountType`。C 端是 `user`，管理端是 `admin`。签名 HS256，密钥和过期时间来自环境变量 `JWT_SECRET`、`JWT_EXPIRATION`。

之后请求头：

```http
Authorization: Bearer <token>
```

`Bearer` 后面有一个空格。

`GlobalAuthInterceptor` 挂在几乎所有路径上。方法上有 `@IgnoreJwt` 的登录、注册会放行。检查顺序：

1. 没有 `Bearer ` → 10004。
2. Redis 键 `token:blacklist:<token>` 已存在 → 10005。登出按 token 剩余寿命写入这个键。
3. 签名失败或过期 → 10005。
4. `admin` 只能访问 `/admin` 开头；普通用户访问管理端路径 → 10004。
5. 普通用户再看状态。先读 Redis `user:status:<id>`，没有再查数据库。状态为 0 → 11004。
6. 通过后把 `LoginUser` 放进请求属性 `userInfo`。

前端保存登录响应里的 `data.token`，后续请求带上 `Bearer`。收到 10004、10005、11004 时清掉本地登录态。

打开：`AuthServiceImpl.login`、`JwtService.generateToken`、`GlobalAuthInterceptor.preHandle`、`BlackListService`。

可以现场串一次：登录 → 带 token 调 `GET /goals` → 登出 → 同一枚 token 再调，得到 10005。

## 用户列表和分页

样板是 `GET /users`。query 进 `UserListRequest`，Service 把页码换成偏移：`offset = (pageNum - 1) * pageSize`，再查一页数据和一条 `COUNT`。

`PageResponse` 有 `pageNum`、`pageSize`、`total`、`data`。外包一层统一响应后，列表在 `data.data`。

`UserMapper.xml` 的 `<sql id="UserWhere">` 被列表和计数共用。`keyword`、`status` 为空时 `<if>` 不拼进 WHERE。`LIMIT #{offset}, #{pageSize}` 只接收 Service 算好的两个数。

实体到响应在 `UserServiceImpl.convertToUserResponse`：时间变成 `yyyy-MM-dd HH:mm:ss`，密码不拷贝。

打开：`UserListRequest`、`UserServiceImpl.getUserList`、`UserMapper.xml`。

## 目标：次数、状态、打卡

`POST /goals` 的 body 有备注、到期时间、周期、`labelId`。周期 1、2、3 对应天、周、月，应打卡次数在 `GoalServiceImpl.createGoal` 里用 `TimeService.getTimeDifference` 算好再插入。

响应里的状态在 `getGoalStatus` 现算，不读表上那一列：

| 值 | 条件 |
| --- | --- |
| 2 | 已打卡次数达到目标次数 |
| 3 | 当前时间晚于到期时间 |
| 1 | 其余情况，进行中 |

次数已经达标时返回 2，即便日期已过。完成率在 `calculateCompletionRate`，次数相除后保留两位。

`GET /goals` 只查 token 对应用户，再按 `labelId` 填标签名。`PATCH`、`DELETE`、打卡都先 `requireGoal`，没有则 14001。现有打卡路径是 `POST /goals/{id}/clockIn`，次数加 1。新接口按 `POST /goals/{id}/clock-ins` 命名。

`GoalMapper.xml` 的查询和更新都带 `user_id`。客户端带了别人的目标 id，也改不到那一行。

打开：`GoalServiceImpl` 的 `createGoal`、`getGoalStatus`、`clockInGoal`，以及 `GoalMapper.xml`。

## 标签

入口 `LabelController`，前缀 `/labels`。创建、列表、删除都用 token 里的 userId。

重名规则在 `LabelServiceImpl.createLabel`：先取出该用户已有标签，名称和类型都相同则抛 `LabelNameAlreadyExists`（13001），否则插入。判断在这次查出来的列表上，不在数据库唯一索引上。

`GET /labels/{id}` 按主键查，方法上没有 `LoginUser`。列表和创建绑定了用户，按 id 读取当前没有按用户过滤。讲的时候把这个差别指出来。

打开：`LabelController`、`LabelServiceImpl.createLabel`。

## 管理端

管理端是另一套登录：`POST /admin/auth/login`。token 里 `accountType` 为 `admin`，只能调 `/admin` 开头的接口。C 端 token 调 `GET /admin/users` 会得到 10004。

`GET /admin/users` 把查询条件抄成 `UserListRequest`，再调用 `userService.getUserList`。分页和 keyword 与 C 端列表相同，差别是路径和 token 种类。

`GET /admin/users/{id}` 额外汇总这个用户的目标：进行中、已完成、已过期的个数来自 `getGoalStatus` 的计算结果。

停用：

```http
POST /admin/users/{id}/status

{ "status": 0 }
```

实现进 `userService.updateUserStatus`：改 `user.status`，并刷新 Redis 键 `user:status:<id>`。该用户下一请求在拦截器得到 11004。

管理端登出标了 `@IgnoreJwt`，C 端 `POST /auth/logout` 没有。C 端登出会先过拦截器。

打开：`AdminAuthController`、`AdminPlatformUserController`、`AdminPlatformUserServiceImpl`、`UserServiceImpl.updateUserStatus`。

## 请求外面的进程

`docker-compose.yaml` 里和这条链路有关的四个服务在同一网络，用服务名访问：

| 服务 | 作用 |
| --- | --- |
| `nginx` | 页面和 `/api` |
| `clock-my-goal` | 9090 上的 jar |
| `mysql` | 业务库 |
| `redis` | 黑名单和用户状态 |

Nginx 的 `/` 托管前端打包结果，找不到文件时回退 `index.html`，history 路由靠这个。`/api/` 转发到应用，并去掉 `/api`。同域时 axios 的 `baseURL` 写 `/api`。

发布时镜像标签与 Compose 里的 `image` 一致，在仓库根目录用 `clock-my-goal/Dockerfile` 构建，再到 `clock-my-goal/docker` 执行 `docker compose up -d`。构建上下文是仓库根目录，因为父 POM 在根上。数据库在数据卷里，更换应用不会清表。`init.sql` 只在数据卷还是空的时候执行。

头像文件和日志各看配置里的路径。`file.accessPrefix` 同时参与写磁盘和静态资源映射；拦截器排除的是 `/static/**`。日志文件名在 `application.yaml` 的 `logging.file.name`。这三处对不上时，先改配置。

## 改一个接口时改哪几处

1. 定 HTTP 方法和路径。
2. 写 Request、Response，参数加上 `@Valid`。
3. 规则写在 Service，失败抛 `BusinessException`。
4. 要查表就补 Mapper 方法和 XML，条件里带上 token 里的 userId。
5. 需要登录的接口不要加 `@IgnoreJwt`。
6. 先直连 `9090` 测，再经 `/api` 测一次。

当场可以改 `GET /goals`：增加可选 query `keyword`，按备注模糊筛选，并且仍然只返回当前用户的目标。不传或为空时行为与现在相同，命中 0 条时 `code` 为 0、`data` 为 `[]`。

落点四处：`GoalListRequest` 用 `@ModelAttribute` 接 query；Controller 把 `keyword` 和 `userId` 交给 Service；Mapper 用 `@Param` 声明这两个名字；XML 用 `<if>` 拼 `remark LIKE`，WHERE 里保留 `user_id`。状态不要放进这条 SQL，响应状态仍由 `getGoalStatus` 计算。

改完用三组请求看结果：不传 `keyword`、传能命中的备注、传命中不了的备注。再换一个用户的 token，确认看不到前一个用户的目标。
